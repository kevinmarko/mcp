## 0. Recommendation, and what this note corrects in the plan

**Recommendation.** Store the index in a dedicated Google Sheet owned by the archive admin (one data tab per
calendar month plus a one-row-per-day ledger tab), written only by a separate hourly time-driven job that reads
the existing archive folder as the installer, and serve it to the app through one `google.script.run` call that
reads the script cache and replies "unchanged" in about 140 bytes when the browser already has the version, exactly
like `getDataFeed`. The cache is only the read path, never the store: it expires in at most 6 hours and caps at
1,000 items, and `PropertiesService` is out because the whole store is 500 KB and already carries every user's prefs.

### 3.2 (a) A Sheet

| Horizon | Rows | Cells at 8 col | % of 10 M | % of 20 M | At 9 col (lane) | At 10 col |
|---|---|---|---|---|---|---|
| 90 days | 81,360 | 650,880 | 6.5% | 3.3% | 732,240 | 813,600 |

| 3 years (1,095 d) | 989,880 | 7,919,040 | 79.2% | 39.6% | 8,908,920 (89%) | 9,898,800 (99%) |

* The cap is per spreadsheet across all tabs. Repo: 10 million (`Code.gs:325`, `README.md:239`). DOC
  (`support.google.com/drive/answer/37603`, fetched): "Up to 20 million cells or 100MB for spreadsheets that are created
  in or converted to Google Sheets"; the page does not mention 10 million. Which applies to this account is
  **UNCONFIRMED**; the design budgets against 10 million. Result: a year fits easily; 3 years at 8 columns fits but is
  79% full, and at 10 columns it is 99% full (no headroom), so plan year-sharded spreadsheets, not one forever Sheet.
* Layout: one data tab per month (`YYYY-MM`, about 28,024 rows and 224,192 cells for a 31-day month) plus a `Days`
  ledger tab. A 30-day window touches at most two tabs; dropping old data is deleting a tab; a rewrite never touches
  more than one month.
* Read cost: the client never reads the Sheet. The server reads it only to rebuild the cached window
  (217,184 cells for 30 days) or on a cache miss. Sheet read and write latency on `/exec` is **UNCONFIRMED** (the checklist
  records it).
* Strengths: human-readable and repairable by Kevin; same service, setup, sharing and test-fake pattern as the config and
  team Sheets (`TeamSheet.gs:661-752`); Sheets revision history for free (UNCONFIRMED how far back).
* Weaknesses: the cell cap; value coercion (set the day and cut-off columns to plain text, or the `sheetText_` problem
  in `TeamSheet.gs:104-124` applies); a visitor-run read needs the Sheet shared (see 4.1).

### 3.3 (b) One Drive JSON file per ISO week or month

| Property | Week | Month |
|---|---|---|
| Raw JSON | ~402 KB (7 x 57.5 KB) | ~1.7 MB |
| Gzip | ~75 KB | ~322 KB |
| Files for a 30-day window | 5 to 6 | 2 |

* No cell cap, denser, and ships to the client as-is.
* Drive has no atomic append: every daily update is read, modify, `setContent` of the whole file, so overlapping writers
  (a manual re-run during the hourly trigger, a backfill) can clobber each other. It needs `LockService`, the same
  script lock that note saves take (`TeamSheet.gs:362-363`; `DataFeeds.gs:225-227` already avoids it for that reason).
* Not editable by a person without tooling; an interrupted write leaves a half-day you cannot see; revision behaviour is
  **UNCONFIRMED**.
* Visitors cannot read an admin-owned file unless it is shared, same as a Sheet.

## 4. The job

All names below are **planned and do not exist**; signatures are illustrative only.

```
refreshHistoryIndex()                 // trigger handler, never throws
installHistoryIndexTrigger()          // editor, admin only, run once
setupHistoryIndex()                   // editor, admin only: create the Sheet + tabs + share
checkHistoryIndex()                   // editor, read-only diagnostic (like checkArchiveFolder)
reprocessHistoryDay(date)             // editor, admin only
getHistoryIndex(request)              // public, google.script.run
```

### 4.1 Trigger and identity

* Follow `installDataFeedTrigger` (`DataFeeds.gs:326-334`): `assertArchiveAdmin_()`, delete any earlier trigger with the
  same handler, create the trigger, run once.
* **Separate hourly trigger, not another step inside `refreshDataFeeds`.** The feed refresh must stay about 2 s and is
  already extended by the archive cache (`DataFeeds.gs:308-318`, up to 90 s); a separate trigger isolates run time and
  failure emails. Hourly rather than daily because the day's Sheet is added by hand at an unknown hour, and DOC says
  time-driven triggers are randomised within the hour ("Apps Script chooses a time between 9 AM and 10 AM"). Most runs
  find nothing new and exit after a folder listing. Per-run time is **UNCONFIRMED** (the feed refresh is "~2 s" per
  `README.md:310`). Trigger count: DOC limit "20 / user / script"; this project has about two.
* The trigger **runs as the installer** (DOC: "Installable triggers always run under the account of the person who
  created them"; `DataFeeds.gs:324-325`; `Code.gs:566-568`). Consequences:
  1. The installer must be able to open the archive folder; Viewer is enough (`Code.gs:484-485`, `README.md:264-266`).
     Install as the same admin account that holds `bfrArchiveAdmin` (`Code.gs:725-737`).
  2. The History Sheet is created by and owned by that account. Web-app visitors run as themselves
     (`TeamSheet.gs:13-18`), so a visitor-run cache miss can read it only if it is shared. Share org VIEW only, as the
     config Sheet is (`TeamSheet.gs:730`); only the trigger writes.
  3. If that account is removed or loses folder access the trigger fails (and DOC says Apps Script emails the owner
     "Your script has recently failed to finish successfully"); this is D5's "who owns the installing account"
     question in another form.
  4. The job uses only services the project already uses (`DriveApp`, `SpreadsheetApp`, `UrlFetchApp`,
     `ScriptApp.getOAuthToken`, `CacheService`, `LockService`), so no new OAuth consent is expected. **UNCONFIRMED** until
     the first run on `/exec`.
  5. The job never writes to the archive folder (`Code.gs:330-331`; the retired timer is the reason, `354-359`).

### 4.2 One run, step by step

1. List the folder with the existing `scanArchiveFolder_` (`Code.gs:496`): the same "most recently edited wins" rule the
   Historical Data popover serves, so the index can never disagree with it about which Sheet is a date's.
2. Read the `Days` ledger: one row per day with `day, sourceFileId, sourceUpdatedMs, rows, status, builtAt, note`. A day
   is **todo** when it is missing, its `sourceUpdated` differs (someone edited that day's Sheet), or its status is not `ok`.
   This mirrors the archive cache's own freshness test, id plus last-updated (`Code.gs:669`).
3. Process todo days newest first, until a time budget (90 s, as `Code.gs:585`) is reached. Remaining days wait for the next run.
4. Per day: fetch the day CSV with `archiveDayCsvText_` (`Code.gs:543`, same export, same header check); pick columns
   **by header name** (the live export gained two columns at 0-based indexes 33-34 and moved the 64 columns after them, DATA, a live export not committed to the repo; a positional
   reader would read the wrong measures with no error); skip `VMS`; coerce numbers; normalise dates; build rows.
5. Validate before touching the Sheet: required columns present, row count above zero, and within 30% of the previous day.
   A suspect day is recorded as `suspect` and **does not replace** an existing good day.
6. Under `LockService.getScriptLock().tryLock(...)`, held only for the mutation and not for the fetch or parse (the same lock
   serves note saves, `TeamSheet.gs:362-363`): set the ledger row to `building`, delete that day's contiguous block, insert the
   new block in day order, set the ledger row to `ok` with the row count.
7. If any day changed, rebuild the window payload (gzip, base64, 90,000-char chunks, the md5 of the ledger stamps in the window as the
   `hash`) and `putAll` it with its meta in one call, so a reader never sees a meta without its chunks (the pattern at
   `Code.gs:648-650`). Otherwise re-put the existing chunks if older than 4 hours (`Code.gs:584`, `672`), without reading the Sheet.
8. Log one summary line and store a small last-run status (section 4.4).

**Idempotency.** The key is `(day, vvd, pol)` and every re-run of a day is delete-then-insert of that day's whole block
inside the lock, so it can never duplicate. The ledger row is the commit marker: a crash after step 6's delete leaves
`building`, which the next run treats as todo and rebuilds. A post-write check compares the day's row count with the ledger.
Rows are append-only history otherwise: a day removed from the archive folder keeps its rows (open question 5 covers deleting).

**Backfill** is the same loop with a larger budget (about 4 minutes, under DOC's 6 min/execution) run from the editor until
`remaining` is 0; there is no separate code path. Depth is whatever the folder holds; `checkArchiveFolder` reports `oldest` and
`dates` (`Code.gs:761-763`), which the checklist records first. The committed 9-day CSV is a fixture for tests, not a
production backfill source: the server cannot read the repo. The old single published Sheet (15.9 MB) could be imported once,
but only if Kevin wants dates the folder lacks (open question 5).

### 4.3 Failure handling

| Failure | Behaviour | Where it shows |
|---|---|---|
| Folder missing, trashed or not shared with the installer | Run returns `{ok:false, reason:'folder'}`; no throw | `console.warn`; status property |
| Day export is not HTTP 200 or not the export | That day `failed`, others continue | Ledger `note`; warn |
| A required column is missing | That day `failed: missing <name>`; never writes zeros | Ledger `note`; warn |
| Zero rows, or count outside 30% of the previous day | `suspect`; previous good rows kept | Ledger; warn |
| Script lock busy | Skip the run; retried next hour | One log line |
| Time budget reached | Stop cleanly; `remaining` reported | Summary line |
| Write throws midway | Ledger stays `building`; next run rebuilds the day | Warn |
| Cache refuses the put (size, quota) | Ignored; the next visitor rebuilds from the Sheet behind a claim key (the pattern at `DataFeeds.gs:231-255`) | Warn |
| Sheet full | `failed: sheet-full`; the app keeps serving what exists | Warn; status |

Never let an exception escape the handler, because a throwing trigger emails its owner every run (`DataFeeds.gs:277-278`). Log to the
Executions log (`console.log` summary, `console.warn` per failure) and keep the last run's result in one small script property
(well under 9 KB) so `checkHistoryIndex` can print it. Whether the owner sees other people's runs in Executions is itself
UNCONFIRMED (`README.md:413-414`).

### 4.4 How the app reads it

One call, shaped like `getDataFeed` (`DataFeeds.gs:163-195`):

```
getHistoryIndex({ have: <hash|null>, gzip: <bool>, days: <int, clamped to the window> })
  -> { ok:true, hash, builtAt, ageMs, columns:[...], oldestDay, newestDay, encoding, data }
  |  { ok:true, hash, builtAt, ageMs, unchanged:true }            // about 141 bytes
  |  { ok:false, reason:'not-configured'|'empty'|'busy'|'invalid-request'|'error' }
```

* Validate the request as `getDataFeed` does (type checks, `have` at most 64 chars, `days` clamped).
* `columns` travels with the data so the client reads rows by column name; adding `lane` later does not break an old page.
* The server answers from the cached chunks (meta first; chunks only when the browser needs data). A cache miss reads the
  Sheet as the visitor (needs the org VIEW share), builds, puts, and uses a claim key rather than the script lock.
* Client: reuse `runServerCall` (app `4009-4021`) and the `serverMissing` stop-asking pattern (`4082`, `4131`);
  gunzip with the existing `gunzipBase64` (`4091-4096`); resolve to `null` on any failure so sparklines and persistence simply
  hide; the basic build makes zero server calls (`GOOGLE_SERVICES_OFF`, `3995`, `4000-4003`, `4010`).
* A window of 30 days costs 322,069 B gz (429,428 B base64) on a cold load and about 141 B when unchanged; the full archive for
  the same days would be 4.2 MB and 30 calls.
* The newest archive day lags the live feed (days are added by hand), so the client should merge today's live rows as the final
  point, de-duplicating by day string if today's Sheet has already been archived.

**Server side: yes. Client side: several things are missing, one of them a trap.**

| Need | Present? | Evidence |

| List of available dates, newest first | Yes | `getArchiveIndex()` (`Code.gs:834`, `807-825`); the client already filters, sorts and returns it or `null` (`fetchPerDayArchiveIndex`, app `4022-4042`) |
| Weekends: previous **available**, not yesterday | Yes, trivially | The list holds only dates that have a Sheet. The client picks the greatest date below the as-of date; no calendar logic. What is missing, precisely:

1. A calendar date for the live data (small additive server change: return `fetchedDate` in the script time zone from
   `getDataFeed`, or `asOfDate`), or an agreed rule that the as-of date is the newest index date when its content matches. Not
   possible to decide from the code; open question 7.
2. A client-only loader that calls `fetchPerDayArchiveIndex` and `fetchPerDayArchiveDay` directly, with a keyed cache that
   survives an index refresh, and treats `{ok:false}` as "hide the feature".
3. Optional but worthwhile: let `getArchiveDayCsv` accept `{gzip:true, have}` like `getDataFeed`, cutting the previous-day pull from
   about 0.73 MB to about 0.19 MB (base64) and to about 141 B when unchanged. The cached copy is already gzipped, so it is
   currently being gunzipped on the server to be sent as text (`Code.gs:633-634`).
4. Later: once 2.5 exists, "what changed since the previous date" can be computed from the index (it carries vvd, pol, laden,
   booking, utilisation, cut-off and a PIC-blank flag, 12.9x fewer bytes) instead of the full day, provided `diffSailings` (2.1) is
   expressible in those columns. It cannot see PIC names or other fields, so decide that when 2.1's input is fixed; 2.2 should not wait for 2.5.

## 6. Slice 1.1: the direct-download path

What the code does today (app): the direct path is `fetch(CSV_SOURCE_URL, {cache:'no-store'})`, then
`noteDirectFeedText('live', text)`, then `setDataFeedInfo({via:'direct', fetchedAt:null})` (`8481-8485`).
`noteDirectFeedText` already records `directAt = Date.now()` at that moment (`4084-4089`) and never shows it. The server path
passes `res.fetchedAt` (`8479`) but not `res.ageMs`, which the server sends (`DataFeeds.gs:339`, `347`) and the app drops
(no `ageMs` anywhere in the app). The `older` branch returns `fetchedAt:null` (`4113`) and deliberately leaves `dataFeedInfo`
unchanged (`8478-8479`), so the on-screen data is again the tab's own direct download. The only display is Settings
(`11618-11624`), `toLocaleTimeString()` with no date, so a stamp from yesterday looks like today.

**A truthful stamp on the direct path** is the browser's clock at the moment the download finished, labelled as what it is:
`Downloaded directly by your browser at 10:31 AM` (with the date when not today). That value already exists as `directAt`; the `older`
branch should use it too. Age is then measured on the client's clock from that instant, which has no skew problem. For the server path
use `ageMs` at receipt plus elapsed client time rather than comparing `fetchedAt` with the client clock (the idea the code already uses at
`4104`). Optional skew guard: Google's response sets `access-control-expose-headers: ...Date...` and `access-control-allow-origin: *`
(observed with curl from this sandbox on the live URL, 2026-10-05), so `res.headers.get('Date')` should be readable cross-origin;
a browser read is UNCONFIRMED.

**What cannot be known** (DATA, headers of the live published CSV, observed 2026-10-05):

| Wanted | Why not |
|---|---|
| When the source Sheet last changed | No `Last-Modified` and no `ETag`; `cache-control: private, max-age=300`; the `Location` of the redirect carries a millisecond number that tracks the **request** time, not a change time (three requests gave `...050000`, `...065000`, `...070000`, each matching that request's `Date` to within 2 s) |
| When the upstream data was cut | The Sheet's own edit time is not that either; nothing in the CSV says |
| Publication lag | Google republishes "to the web" with a delay of up to about 5 minutes (UNCONFIRMED, from memory); `cache:'no-store'` defeats the browser cache, not Google's lag |
| The server's view of change time | The repo holds only the publish token (`2PACX-...`, `DataFeeds.gs:36-37`), not a Drive file id, so `getLastUpdated()` is not available without new configuration (UNCONFIRMED whether the admin can open the source file) |

So both paths can say only "downloaded at"; neither can say "data as of". One server-side improvement is possible with no new
access: `fetchedAt` advances every 30 minutes even when the content is identical (`DataFeeds.gs:266-269`), so adding a `changedAt` that is
carried over while the hash is unchanged would give "last changed as we saw it", a more honest "data as of" than `fetchedAt`. About a handful of
lines in `downloadFeed_`; deferred until D8 allows server work (open question 9). Copy for the banner is R6's.

### Method

Parsing: a small RFC 4180 parser (quotes, doubled quotes, CRLF and LF, newlines inside quotes); records counted from it, never from line counts.
Sizes: `JSON.stringify` of the row arrays, `zlib.gzipSync` level 9, base64 length for cache sizing, windows tiled from the nine real days (sizes
only). Per-day full CSVs were rebuilt by record from the parsed rows. Parse time: the repo's SheetJS in Node, warm runs 63 to 405 ms. Live-feed
checks (headers, size, date shapes, column list) were made once on 2026-10-05 from this sandbox against the app's own published link; the body was
kept only in the scratchpad and nothing from it is committed.
