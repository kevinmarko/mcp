# Deploying as a Google Apps Script Web App

The report is a single self-contained HTML file with no server-side dependency
(it fetches its own data client-side from the published Sheet CSV link — see
`CSV_SOURCE_URL` in the main app file). Apps Script's job here is only to
**host that HTML behind an org-restricted URL** — `Code.gs` in this folder is
the entire server-side code required.

This is a manual, account-level process (Google account/project setup) that
has to be done by hand in the Apps Script UI — it isn't something that can be
scripted from this repo.

## One-time setup

1. Go to **[script.google.com](https://script.google.com/)** → **New project**.
2. Rename the project (top left) to something recognizable, e.g. *Booking Flash Report App*.
3. In the file list on the left, click the **+** next to *Files* → **HTML**, and name the new file exactly `index` (Apps Script appends `.html` automatically).
4. Open **`dist/index.html`** in this repo — that is the file to paste, NOT the versioned
   source file in the repo root.

   **Why the artifact and not the source (2026-09-19).** Both produce a working app. The source
   file ships its JSX uncompiled and lets Babel Standalone compile it in the browser on every
   load, which measured at **5,261 ms of one unbroken main-thread task per load**, before any
   data appears — paid by every user, every time, on every tab. `dist/index.html` is the same
   app with that compile already done: first React commit drops from 5,858 ms to 416 ms. It is
   generated by `node scripts/build_deployable.js` and committed, so this step stays a
   copy/paste and needs no tooling on your machine. If you have just changed the app, make sure
   the build was re-run — CI's `deployable-build` job fails when the committed artifact is stale.

   The old instructions pasted the main source file, which for reference is
   `Booking_flash_report_na_2.0_WORKING_PRO_ONLY.html`. **Confirm it by name, do not infer it
   from the version number alone.** Since the 2026-09-17 rename to 2.0 the highest dotted
   version *is* the main file again, but that was false for two weeks and cost real time:
   higher-numbered files also exist as *testing* versions developed on their own branches
   (`1.67_TESTING` is per-user filter/view persistence; `1.70_Testing` was an earlier one), so a
   high number can still mean "newest experiment",
   not "what should be live". Following the old rule would quietly deploy a testing build to
   production. See the main [README](../README.md)'s "Current version" note, which records which
   file is actually the main one — check it rather than inferring from filenames.
   — but you do not paste that file any more. Copy **`dist/index.html`**'s entire contents and
   paste them into the `index.html` file you just created in the Apps Script editor, replacing
   the placeholder content. The artifact carries a header comment naming the source file and its
   SHA-256, so a deployed copy can always be traced back to the exact source it was built from.
5. Open the default `Code.gs` file in the Apps Script editor and replace its contents with **[Code.gs](Code.gs)** from this folder (it's short — just copy/paste it directly). Then add two more script files (**+** next to *Files* → **Script**) named `DataFeeds` and `TeamSheet`, pasting **[DataFeeds.gs](DataFeeds.gs)** and **[TeamSheet.gs](TeamSheet.gs)** — see "Team features" below. `Code.gs` needs them: its `doGet` calls `readAppConfig_`, which lives in `TeamSheet.gs`.
6. Click **Deploy → New deployment**.
7. Click the gear icon next to "Select type" → choose **Web app**.
8. Fill in:
   - **Description**: e.g. `v1`
   - **Execute as**: `User accessing the web app` — every Drive action then runs as the
     person using the report, not as you (see "Extended server features" below). Changed from
     `Me` on 2026-09-28; an existing deployment must be edited to this setting, see below.
   - **Who has access**: `Anyone within [your organization]` — this is what restricts the report to people signed into a company Google account
9. Click **Deploy**. The first time, Google will prompt you to authorize the script — approve it. Every other user also sees a one-time consent screen the first time they open the report (Drive, for their own account).
10. Copy the **Web app URL** it gives you (ends in `/exec`) — that's the stable link end users will open. Save it somewhere durable (send it to Claude too, so it can be recorded).

## Verifying it worked

Open the `/exec` URL in a browser while signed into a company Google account.
It should load the report and auto-fetch data from the published Sheet, same
as the local dev server does. Try opening it in an incognito window signed
into a *non*-company Google account (or signed out) to confirm access is
actually restricted, not just hidden.

## Updating after a code change

Whenever the app's HTML file changes (a new version/fix), the deployment
does **not** update itself automatically — repeat this each time:

1. Rebuild the artifact if it is not already current: `node scripts/build_deployable.js`
   (or just confirm CI is green — the `deployable-build` job fails on a stale artifact).
2. Go back to [script.google.com](https://script.google.com/) and open the project.
3. Open `index.html` in the editor, select all, delete, and paste in **`dist/index.html`**'s full contents.
4. Click **Deploy → Manage deployments**.
5. Click the pencil/edit icon on the existing deployment (don't create a new one — that would change the URL).
6. Under **Version**, choose **New version**, then click **Deploy**.

This keeps the same `/exec` URL stable across updates — end users never need
a new link.

### Redeploying `Code.gs` itself (required once, for the update-checker/reload fix)

`Code.gs` in this folder is not just a passthrough anymore (2026-09-10) — it now
also injects the real `/exec` URL into the page as `window.__EXEC_URL__` and
serves a tiny `?check=version` endpoint, both of which the app's "new version"
banner needs to work correctly *on this deploy path specifically* (see
`index.html`'s `appUpdateAvailable`/`checkForAppUpdate` comments for the full
root-cause story — in short, this app runs inside Apps Script's sandboxed
iframe, whose own URL is a transient one Google's sandbox won't let it
navigate to or usefully re-fetch).

**Until this updated `Code.gs` is deployed** (steps above — same "Manage
deployments → edit → New version" flow, just for `Code.gs` instead of
`index.html`), the app degrades gracefully rather than breaking: the update
banner simply won't offer a working "Refresh Now" action (it tells the user
to refresh the tab manually instead) and won't poll for new versions at all
on this deploy path — it does **not** fall back to the old broken behavior
(the blank-page-on-refresh / phantom-nag bug this fix addresses). So there's
no urgency-driven risk in leaving an old `Code.gs` deployed for a while, but
redeploying it is what actually turns the fix on.

### Server-backed preferences: `window.__SERVER_PREFS__` and `saveUserPref` (2026-09-16)

`Code.gs` also persists the app's three user preferences (dark mode, auto-refresh, freeze panes)
server-side, namespaced by the visitor's email, so they survive the sandbox iframe's rotating
origin instead of resetting every time `localStorage` loses them. Full design reasoning —
why `getScriptProperties()` instead of `getUserProperties()`, the `autoRefresh` null-vs-`'0'`
asymmetry, why there's no async read path — is in `AGENTS.md`'s "Server-backed preferences"
section; this is just what the two pieces are:

- **`window.__SERVER_PREFS__`** — injected by `doGet` as a plain inline `<script>`, placed
  before `index.html`'s own `<script type="text/babel">` block, the same way `__EXEC_URL__`
  already is. It's synchronous, so it's available before the app's first render — there is no
  loading/unknown state for preferences, matching how the app already reads `localStorage`
  synchronously today. When the visitor's identity resolves, it carries `{available: true,
  values: {...}}`; when it doesn't (blank email, `PropertiesService` threw), it carries
  `{available: false, reason: 'no-user-identity'}`. On any non-Apps-Script serving path
  (localhost, static hosting) the global is simply absent, and the app falls back to
  `localStorage` exactly as it does today.
- **`saveUserPref(key, value)`** — a public (no leading-underscore) function callable via
  `google.script.run`, fire-and-forget from the client. It validates `key` is one of the three
  known preference names and `value` is `'1'` or `'0'`, rejecting anything else without writing.
  A failed or rejected write never blocks or reverts the client's own `localStorage` write,
  which always happens first and unconditionally.

**Like the update-checker fix above, this needs `Code.gs` redeployed to take effect**, and
degrades the same safe way in the meantime: with the old `Code.gs` still live,
`window.__SERVER_PREFS__` is simply never injected, so the client-side resolution logic falls
through to `localStorage` exactly as it does today. Nothing breaks by leaving an old `Code.gs`
deployed; redeploying is what turns the feature on.

**This cannot be verified from a dev machine** — `google.script.run` only exists inside the Apps
Script sandbox, so a local server or `file://` load can only confirm the localStorage-only
fallback path, never the actual server round trip. See AGENTS.md's deployed-URL checklist
(same section) for how to check it for real once deployed — in short, a second, independent
browser context (incognito or a different browser) signed into the same account is the only
check that can tell a working round trip apart from `localStorage` simply still being there, and
a second, different account is what confirms preferences aren't leaking between visitors. Nobody
has run that checklist yet as of this writing.

### `?check=identity` — a temporary diagnostic (2026-09-16)

`Code.gs` also serves `?check=identity`, which returns a small JSON report
answering a question Google's documentation leaves genuinely ambiguous: under
"Execute as: Me", does `PropertiesService.getUserProperties()` give each
visitor their own store, or does everyone share the owner's?

That answer gates whether user preferences (dark mode, auto-refresh, freeze
panes) can be moved server-side to survive the sandbox's rotating origin. If
the store turns out to be owner-keyed, building on it would make one person's
dark-mode toggle flip it for the entire organization — and no browser-side
test could catch that, because from the client's point of view the server
would be working perfectly.

**Using it** (needs this `Code.gs` redeployed, and two different org accounts):

1. Open `<exec-url>?check=identity` as yourself. Expect `FIRST_RUN`.
2. Open the same URL as a **different** account. `FIRST_RUN` again is the
   good answer — it means that account has its own empty store.
   `SHARED_ACROSS_USERS` means it read your stamp, and the server-backed
   approach is off the table as designed.
3. Reload as yourself. Expect `STABLE_FOR_SAME_USER`. This step is what rules
   out "the store isn't persisting at all", which would otherwise look like
   success in step 2.

Also read `activeUserEmail`: if it resolves to a real address, there is a
workable fallback even when the store is shared. If it is blank, there is no
per-user key available on this deployment.

Record the result in `AGENTS.md`, then delete `runIdentityProbe_`, its `doGet`
branch, and this section — and run `deleteIdentityProbeStamp_()` once from the
Apps Script editor so it doesn't leave an email address in the property store.
It reports the caller's own address and the last caller's; access is already
limited to the organization, but it is a diagnostic, not a feature.

### Extended server features: filter-prefs sync, Drive export (2026-09-28)

Alongside the three-boolean server-backed prefs above, `Code.gs` now also
persists a per-user copy of `FilterPrefsStore`'s filter blob and backs an
on-demand "Export to Drive" button in Settings. Full design reasoning is in
`docs/SERVER_PREFS_CONTRACT.md`'s "Addendum (2026-09-28)" section and
`Code.gs`'s own comment above `readServerExtras_`; this is just the
deployment-relevant part. (A schedule-change digest email was also built in
this PR and archived before deploying — see that addendum's "Archived"
section.)

**Runs as the visitor, not the deploying account.** This deployment is
"Execute as: User accessing the web app" (changed 2026-09-28). Exports are
created in the visitor's own Drive. To switch an existing deployment:
**Deploy → Manage deployments → pencil → Execute as: User accessing the web
app → New version → Deploy** (same `/exec` URL). Under the old "Execute as:
Me", exports landed in Kevin's Drive behind a link the visitor couldn't open.

**Consent on first open, per user.** After the redeploy, each person sees a
one-time Google consent screen for Drive. There is no Gmail or Calendar
scope — "Add to Calendar" is a plain `calendar.google.com` deep link that
already opens on the visitor's own account.

**Until redeployed**, none of this does anything — `window.__SERVER_EXTRAS__`
is simply never injected, and every gated code path treats that as
unavailable, exactly like the three-boolean prefs feature degrades on an
old `Code.gs`.

**A "Booking Flash Snapshots" folder is created automatically** in the
visitor's own My Drive the first time they export.

**This cannot be meaningfully verified from a dev machine**, for the same
reason the three-boolean prefs can't: `google.script.run` only exists inside
the Apps Script sandbox. A local run can only prove the app degrades
correctly when `window.__SERVER_EXTRAS__` is absent. To verify for real,
after redeploying:

1. Open the `/exec` URL, set a filter (e.g. select a Lane), and confirm it
   is still selected after a reload in an **independent** browser context
   (incognito or a different browser) — the discriminating check, same as
   the three-boolean prefs' own checklist.
2. As a **second, non-deploying account**, click "Export to Drive" and
   confirm the Sheet appears in *that account's* "Booking Flash Snapshots"
   folder and the "View in Drive" link opens it. Nobody has run this
   checklist yet as of this writing.

## Scheduled historical archive, one file per day (2026-09-29)

`Code.gs` can now build the Historical Data archive itself, replacing the manual daily append to
the published archive Sheet. Once a day a timer downloads the live export (the app's
`CSV_SOURCE_URL`) and saves it as one CSV file per date in a Drive folder named **Booking Flash
Archive**, with a small index file. The app then downloads the date list and only the day(s)
someone views, instead of the whole archive. Why per-day: a single Sheet caps at 10 million cells,
and at ~95,000 cells a day the old archive Sheet fills up after roughly 105 days (around early
December 2026). It was also 15.9 MB / ~14 s to load at ~22k rows. Full design notes: `Code.gs`'s
comment above `splitCsvRecords_`.

Nothing changes for users until this is set up: the app only uses the per-day archive when
`?archive=index` returns at least one date, and otherwise falls back to the published Sheet exactly
as before.

**Setup (once, after pasting the new `Code.gs` and redeploying):**

1. In the Apps Script editor, open **Project Settings** and set the **time zone** to the one the
   team works in. The date saved as "Record Date" is today's date in this time zone when the job
   runs.
2. Check `ARCHIVE_RUN_HOUR_` near the top of the archive section in `Code.gs` (default **20**,
   i.e. 8 pm; Google starts the job at some minute between 8 and 9 pm). It should be after the
   live data's last refresh of the day, so each date's file is that day's end-of-day data.
3. Run **`installArchiveTrigger`** from the editor's function menu and approve the permissions it
   asks for (Drive, external requests, triggers). This creates the Drive folder and the daily
   timer. **The timer runs as the account that runs this step**, and that account becomes the
   archive admin: only it can re-run `installArchiveTrigger` or the backfill. Use your account or
   a shared team account, and keep it able to read the live CSV.
4. Run **`backfillArchiveFromLegacySheet`** to copy the existing archive Sheet into per-day files.
   Check the log: it prints `remaining`; if that's above 0 it stopped before Apps Script's
   6-minute limit, so run it again until it's 0. Dates that already have a file are skipped, so
   re-running is safe.
5. In Drive, share the **Booking Flash Archive** folder with the organization (or the team) as
   **Viewer**. Once only; see "Who can read it" below.
6. Open the report as a **different account** from step 3, click **🗓️ Historical Data**, and
   confirm the dates appear and one of them opens. Testing as the admin account alone won't catch a
   missing share.

**Who can read it.** The web app runs as the visitor ("User accessing the web app"), so each
visitor reads the archive with their own Google account, through `google.script.run`
(`getArchiveIndex` / `getArchiveDayCsv`). That's why step 5 shares the folder: without it, a
visitor's read fails and the popover quietly falls back to the old Sheet. Files the timer adds
later inherit the folder's sharing, so this is a one-time step. (The `?archive=` `doGet` URLs do
the same thing for a deployment without `google.script.run`; the app doesn't use them inside Apps
Script, because a plain request to `/exec` from the page carries no sign-in.)

**If a day fails,** the job throws and Google emails the timer's owner a failure notice (for
example if the live CSV returned a sign-in page instead of the export). Nothing is written for
that day, and the next day's run works normally. To fill a missed day, run
`snapshotLiveDataToArchive` from the editor that same day, signed in as the archive admin. It can
only save *today's* data, so a day missed entirely stays missing.

**If the job can't open the archive folder** (it was trashed, or the admin account lost access),
it stops with an error naming the folder and changes nothing. It never quietly starts a new, empty
folder. Restore the folder or the admin's access. Only if the folder is really gone, delete the
`bfrArchiveFolderId` script property (Project Settings → Script properties) and run
`installArchiveTrigger` again, which creates a new folder that needs sharing again.

**Only the archive admin can run the daily job.** The job, `installArchiveTrigger` and the
backfill all check the caller, so a visitor calling them from the page does nothing. The timer
runs as the admin, so it passes.

**Transition from the manual archive.** Hoa can keep appending to the old Sheet while the timer
runs; the backfill never overwrites a date that already has a file, and the app ignores the old
Sheet once the per-day archive has dates. Once the timer has run for a few days and the popover
looks right, the manual append can stop.

**Not verifiable locally.** `tests/check_archive_logic.js` runs this `Code.gs` against simulated
Google services and the committed fixtures, and regression Suite 17 exercises the app's side
against a fake archive. Neither proves real Drive permissions, trigger timing, or that Google's
servers can fetch the published CSV, so the setup steps above are the real test.

## Team features: data cache, VVD notes, startup-error log, config Sheet (2026-09-29)

Two new script files add four features. Each one degrades to today's behavior until it is set up, so
deploying the code first and setting up later breaks nothing.

| Feature | What it does | Needs the Sheets? |
|---|---|---|
| Data cache (`getDataFeed`) | A trigger (`refreshDataFeeds`) downloads the live and sector CSVs server side every 30 minutes from 8:00 to 17:00 and hourly outside that (in the script's time zone, every day) and keeps them in the script cache; browsers get the cached copy gzipped, or a tiny "unchanged" reply when they already have it. So the data on screen is up to ~30 minutes older than the published Sheet during the day and up to ~1 hour otherwise. If the server copy isn't ready within 8 seconds, or anything fails, the app fetches the published Sheet directly, as before. | No |
| VVD notes | One note per VVD per person, visible to everyone. | Team Data |
| Startup-error log | When the app fails to start on someone's machine, the reason is logged. | Optional (Team Data); always in the Executions log |
| Config Sheet | Edit the schedule-change thresholds, the Sector Summary lane exclusions and the port-exclusion list in a Sheet instead of the source. | Config |

**Setup (once):**

1. In the Apps Script editor click **+** next to **Files** -> **Script**, name it **DataFeeds**, and paste
   `apps-script/DataFeeds.gs`. Repeat with the name **TeamSheet** and `apps-script/TeamSheet.gs`. Also paste
   the updated `Code.gs` (one new line in `doGet`). File order does not matter.
2. **Deploy -> Manage deployments -> edit (pencil) -> Version: New version -> Deploy**, as in "Redeploying
   `Code.gs` itself" above.
3. Run **`installDataFeedTrigger`** once from the editor's function menu, as the **archive admin**. It
   installs the `refreshDataFeeds` trigger. It runs every 30 minutes; from 8:00 to 17:00 every run
   re-downloads both CSVs, and outside those hours it skips a copy under 45 minutes old, so it is hourly
   (about 2 s per download, ~1 minute of trigger time a day). The hours use the script's time zone
   (**Project settings -> Time zone**); change them with `DATA_FEED_BUSY_START_HOUR_` /
   `DATA_FEED_BUSY_END_HOUR_` in `DataFeeds.gs`. Why it matters: every
   open tab auto-refreshes at the same moment, so without the trigger the whole org would find the cached
   copy expired at once and wait on one download. The trigger also re-fills the config cache if Google evicts
   it, so page loads never open the config Sheet. It works without the trigger, just slower at those moments.
4. Run **`setupTeamSheets`** once from the editor's function menu, as the **archive admin** (the same
   account as `installArchiveTrigger`; anyone else is refused) and approve the Sheets / Drive / triggers
   permissions. It creates **Booking Flash Team Data** (tabs `VVD Notes`, `Startup Errors`) and **Booking
   Flash Config** (tabs `Settings`, `Port Exclusions`, pre-filled with the values the app uses today), shares
   them, and installs the config Sheet's edit trigger. The log shows both URLs. It is safe to run again: it
   only creates what is missing and never overwrites rows.
5. Confirm the sharing (the result's `sharing` field says `ok` or why it failed; a failure does not stop the
   rest). Open each Sheet -> **Share**:
   - **Booking Flash Team Data: anyone in the organization can EDIT.** This is required, because the web app
     runs as each visitor and writes notes and error rows as them. **It also means anyone in the org could
     edit or delete another person's note directly in the Sheet.** The "only the author can change a note"
     rule is enforced by the app and `saveVvdNote`, not by Sheets.
   - **Booking Flash Config: anyone in the organization can VIEW**, and only the admin edits (visitors read
     it as themselves when the page loads).
6. Test as a **different account** from step 3: add a note on a VVD and reload as a third account to see it;
   confirm the account cannot change the other's note.

**Editing the config.** Change a value in the `Settings` tab (keys and defaults are pre-filled, one line of
explanation each) or the `Port Exclusions` tab, which replaces the app's built-in port list when present
(header only = exclude nothing; delete the tab = use the built-in list). A blank value means "use the app's
default". The edit trigger re-reads the Sheet into the server's cache as soon as you edit, so the next page
load picks it up without opening the Sheet itself. If an edit doesn't show up (edit trigger removed), run
**`refreshAppConfig`** from the editor.
The app validates every value itself: a bad value (`abc`, `0`, a lane code with symbols) is ignored for that
key only, the default is used, and the app's **⚙️ Settings** panel lists the ignored value (also logged to
the browser console as a `[config sheet]` warning). Settings also shows how many config values are in effect.

**Startup errors.** Rows appear in the Team Data `Startup Errors` tab (time, user, reason, errors, whether React
loaded, browser, page). Every report is also written to the script's **Executions** log as a line starting
`[startup-error]`, even when the Sheet is not set up or a user is rate-limited (5 reports per person per 10
minutes). Unverified: because the app runs as each visitor, the Executions page may not show the owner the
log text of other people's runs -- treat the Sheet tab as the reliable place and check both after setup.
The report is only sent from inside Apps Script; the error box itself says "These details were sent to the
report owner automatically" when it went through.

**Not verifiable off-Google.** `tests/check_team_features_logic.js` runs the real `.gs` files against simulated
Google services and the app's own config validator. It does not prove real Sheets sharing, that visitors' own
accounts can open the two Sheets, that the edit trigger fires, the sign-in redirect the data cache rejects,
script-cache limits and lock timing under real load, or Google's own handling of leading `=` / apostrophe
text. The setup steps above, run as two different accounts, are the real test.

## Running a testing version alongside the main one

Per Kevin (2026-09-16): **one `Code.gs` per Apps Script project, not two.** An Apps Script
project is a single global JavaScript namespace, so a second copy of this file in the same
project means two `doGet` declarations and the editor rejects it outright
(`Identifier 'doGet' has already been declared`). The same goes for every other function here.

To have the main version (1.66) and a testing version (e.g. 1.67) both reachable, create **two
separate Apps Script projects**, each with its own `Code.gs`, its own `index.html`, and its own
`/exec` URL. The `Code.gs` source is identical in both — it is version-agnostic and simply serves
whatever HTML is sitting in its project's `index.html`. Nothing in this file needs to know which
app version it is hosting.

Two consequences worth knowing before you debug something that is not a bug:

- **Script properties are per-project.** Each project has its own store, so the preferences saved
  by the server-backed prefs feature do NOT cross between the two deployments. Dark mode set on
  the testing deployment will not appear on the main one. For testing that is the behaviour you
  want — a testing build cannot corrupt real settings — but do not read it as the feature being
  broken.
- **The update-checker compares against its own project's `index.html`.** Each deployment
  independently decides whether it is out of date, which is correct, but it means a version
  banner on one says nothing about the other.

Label the projects clearly in the Apps Script UI (e.g. *Booking Flash Report App* vs *Booking
Flash Report App — TESTING*). The two `/exec` URLs are opaque and indistinguishable by eye, and
pasting a testing build over the live project is a quiet, expensive mistake to make.

## Optional: automating updates with `clasp`

If copy-pasting on every update becomes annoying, Google's
[`clasp`](https://github.com/google/clasp) CLI can push a local file straight
into an Apps Script project from the command line (`clasp push`), which could
be scripted from this repo instead of the manual copy/paste above. Not set up
here — worth doing later if updates become frequent enough to be worth the
one-time `clasp login`/`clasp clone` setup.
