# Deploying as a Google Apps Script Web App

The report is a single self-contained HTML file with no server-side dependency
(it fetches its own data client-side from the published Sheet CSV link — see
`CSV_SOURCE_URL` in the main app file). Apps Script's job here is only to
**host that HTML behind an org-restricted URL** — `Code.gs` in this folder is
the entire server-side code required.

This is a manual, account-level process (Google account/project setup) that
has to be done by hand in the Apps Script UI — it isn't something that can be
scripted from this repo.

## One-time setup

1. Go to **[script.google.com](https://script.google.com/)** → **New project**.
2. Rename the project (top left) to something recognizable, e.g. *Booking Flash Report App*.
3. In the file list on the left, click the **+** next to *Files* → **HTML**, and name the new file exactly `index` (Apps Script appends `.html` automatically).
4. Open **`dist/index.html`** in this repo — that is the file to paste, NOT the versioned
   source file in the repo root.

   **Why the artifact and not the source (2026-09-19).** Both produce a working app. The source
   file ships its JSX uncompiled and lets Babel Standalone compile it in the browser on every
   load, which measured at **5,261 ms of one unbroken main-thread task per load**, before any
   data appears — paid by every user, every time, on every tab. `dist/index.html` is the same
   app with that compile already done: first React commit drops from 5,858 ms to 416 ms. It is
   generated by `node scripts/build_deployable.js` and committed, so this step stays a
   copy/paste and needs no tooling on your machine. If you have just changed the app, make sure
   the build was re-run — CI's `deployable-build` job fails when the committed artifact is stale.

   The old instructions pasted the main source file, which for reference is
   `Booking_flash_report_na_2.5_WORKING_PRO_ONLY.html` (since 2026-10-11, when the 2.5 testing build
   was promoted to production; before that it was `Booking_flash_report_na_2.0_WORKING_PRO_ONLY.html`). **Confirm it by name, do not infer it
   from the version number alone.** Since the 2026-09-17 rename to 2.0 the highest dotted
   version *is* the main file again, but that was false for two weeks and cost real time:
   higher-numbered files also exist as *testing* versions developed on their own branches
   (`1.67_TESTING` is per-user filter/view persistence; `1.70_Testing` was an earlier one), so a
   high number can still mean "newest experiment",
   not "what should be live". Following the old rule would quietly deploy a testing build to
   production. See the main [README](../README.md)'s "Current version" note, which records which
   file is actually the main one — check it rather than inferring from filenames.
   — but you do not paste that file any more. Copy **`dist/index.html`**'s entire contents and
   paste them into the `index.html` file you just created in the Apps Script editor, replacing
   the placeholder content. The artifact carries a header comment naming the source file and its
   SHA-256, so a deployed copy can always be traced back to the exact source it was built from.
5. Open the default `Code.gs` file in the Apps Script editor and replace its contents with **[Code.gs](Code.gs)** from this folder (it's short — just copy/paste it directly). Then add three more script files (**+** next to *Files* → **Script**) named `DataFeeds`, `TeamSheet` and `Shared`, pasting **[DataFeeds.gs](DataFeeds.gs)**, **[TeamSheet.gs](TeamSheet.gs)** and **[Shared.gs](Shared.gs)** — see "Team features" below. `Code.gs` needs the first two: its `doGet` calls `readAppConfig_`, which lives in `TeamSheet.gs`. `Shared.gs` is **generated** by `node scripts/sync_shared.js` from `shared/` (never edit it by hand) and defines the global `BFShared`; it must be in the Apps Script project, or anything that calls `BFShared` fails with a `ReferenceError`.
6. Click **Deploy → New deployment**.
7. Click the gear icon next to "Select type" → choose **Web app**.
8. Fill in:
   - **Description**: e.g. `v1`
   - **Execute as**: `User accessing the web app` — every Drive action then runs as the
     person using the report, not as you (see "Extended server features" below). Changed from
     `Me` on 2026-09-28; an existing deployment must be edited to this setting, see below.
   - **Who has access**: `Anyone within [your organization]` — this is what restricts the report to people signed into a company Google account
9. Click **Deploy**. The first time, Google will prompt you to authorize the script — approve it. Every other user also sees a one-time consent screen the first time they open the report (Drive, for their own account).
10. Copy the **Web app URL** it gives you (ends in `/exec`) — that's the stable link end users will open. Save it somewhere durable (send it to Claude too, so it can be recorded).

## Verifying it worked

Open the `/exec` URL in a browser while signed into a company Google account.
It should load the report and auto-fetch data from the published Sheet, same
as the local dev server does. Try opening it in an incognito window signed
into a *non*-company Google account (or signed out) to confirm access is
actually restricted, not just hidden.

## Updating after a code change

Whenever the app's HTML file changes (a new version/fix), the deployment
does **not** update itself automatically — repeat this each time:

1. Rebuild the artifact if it is not already current: `node scripts/build_deployable.js`
   (or just confirm CI is green — the `deployable-build` job fails on a stale artifact).
2. Go back to [script.google.com](https://script.google.com/) and open the project.
3. Open `index.html` in the editor, select all, delete, and paste in **`dist/index.html`**'s full contents.
4. Click **Deploy → Manage deployments**.
5. Click the pencil/edit icon on the existing deployment (don't create a new one — that would change the URL).
6. Under **Version**, choose **New version**, then click **Deploy**.

This keeps the same `/exec` URL stable across updates — end users never need
a new link.

### Redeploying `Code.gs` itself (required once, for the update-checker/reload fix)

`Code.gs` in this folder is not just a passthrough anymore (2026-09-10) — it now
also injects the real `/exec` URL into the page as `window.__EXEC_URL__` and
serves a tiny `?check=version` endpoint, both of which the app's "new version"
banner needs to work correctly *on this deploy path specifically* (see
`index.html`'s `appUpdateAvailable`/`checkForAppUpdate` comments for the full
root-cause story — in short, this app runs inside Apps Script's sandboxed
iframe, whose own URL is a transient one Google's sandbox won't let it
navigate to or usefully re-fetch).

**Until this updated `Code.gs` is deployed** (steps above — same "Manage
deployments → edit → New version" flow, just for `Code.gs` instead of
`index.html`), the app degrades gracefully rather than breaking: the update
banner simply won't offer a working "Refresh Now" action (it tells the user
to refresh the tab manually instead) and won't poll for new versions at all
on this deploy path — it does **not** fall back to the old broken behavior
(the blank-page-on-refresh / phantom-nag bug this fix addresses). So there's
no urgency-driven risk in leaving an old `Code.gs` deployed for a while, but
redeploying it is what actually turns the fix on.

**`getAppVersionHash()` (2026-10-06).** Under **Execute as: User accessing the web app** a plain `fetch()`
of `<exec-url>?check=version` from the page carries no Google sign-in, so it likely gets Google's sign-in
page back instead of the hash, and the "new version" banner then never appears. `Code.gs` therefore also
has a public function, `getAppVersionHash()`, that the page can call through `google.script.run` (which runs
as the signed-in visitor). It returns exactly what `?check=version` answers: a plain string, the
32-character lowercase hex MD5 of the deployed `index.html` (for example
`"9e107d9d372bb6826bd81d3542a419d6"`). The `?check=version` route is unchanged, for pages already open
from older builds. Whether the plain fetch really gets a sign-in page, and whether the banner works through
`google.script.run`, are **UNCONFIRMED** until checked on `/exec`: open the page, pick the inner frame in the
DevTools console (`typeof window.__EXEC_URL__` is `"string"` there) and run
`google.script.run.withSuccessHandler(console.log).getAppVersionHash()`; expect a 32-character hex string,
and the same string from a signed-in browser tab opened on `<exec-url>?check=version`.

**The banner itself after a redeploy (UNCONFIRMED, 2026-10-07).** That a call returns a hash does not show that
an already-open page ever sees a *new* one. If `google.script.run` from a page keeps running the deployment
version that served that page, the hash it gets back never changes and the banner never appears; nothing in
this repo can tell, since the tests fake `google.script.run`. To check: (1) open `/exec` and leave the tab open;
(2) change `index.html` (any harmless edit), then **Deploy -> Manage deployments -> edit -> New version** on the
same deployment; (3) wait up to 5 minutes (one `APP_UPDATE_POLL_INTERVAL_MS`) in the open tab. Pass: the "new
version" banner appears. Fail: no banner after 10 minutes, and the console call above, run in the OLD tab, still
returns the old hash while a freshly opened tab returns the new one. On a fail, nothing in the page can see the
new version from that tab, so the fix would be server-side and is a decision for Kevin. `getAppVersionHash` is
deliberately not cached (see its comment in `Code.gs`).

### Server-backed preferences: `window.__SERVER_PREFS__` and `saveUserPref` (2026-09-16)

`Code.gs` also persists the app's three user preferences (dark mode, auto-refresh, freeze panes)
server-side, per visitor, so they survive the sandbox iframe's rotating origin instead of
resetting every time `localStorage` loses them. Since 2026-10-06 they live in each visitor's own
**user properties** (see "Where per-user values are stored (2026-10-06)" below); before that, in the
shared script properties namespaced by the visitor's email. Full design reasoning — the
`autoRefresh` null-vs-`'0'` asymmetry, why there's no async read path — is in "Server-backed
preferences (2026-09-16)" at the end of this file; this is just what the two pieces are:

- **`window.__SERVER_PREFS__`** — injected by `doGet` as a plain inline `<script>`, placed
  before `index.html`'s own `<script type="text/babel">` block, the same way `__EXEC_URL__`
  already is. It's synchronous, so it's available before the app's first render — there is no
  loading/unknown state for preferences, matching how the app already reads `localStorage`
  synchronously today. When the visitor's identity resolves, it carries `{available: true,
  values: {...}}`; when it doesn't (blank email, `PropertiesService` threw), it carries
  `{available: false, reason: 'no-user-identity'}`. On any non-Apps-Script serving path
  (localhost, static hosting) the global is simply absent, and the app falls back to
  `localStorage` exactly as it does today.
- **`saveUserPref(key, value)`** — a public (no leading-underscore) function callable via
  `google.script.run`, fire-and-forget from the client. It validates `key` is one of the three
  known preference names and `value` is `'1'` or `'0'`, rejecting anything else without writing.
  A failed or rejected write never blocks or reverts the client's own `localStorage` write,
  which always happens first and unconditionally.

**Like the update-checker fix above, this needs `Code.gs` redeployed to take effect**, and
degrades the same safe way in the meantime: with the old `Code.gs` still live,
`window.__SERVER_PREFS__` is simply never injected, so the client-side resolution logic falls
through to `localStorage` exactly as it does today. Nothing breaks by leaving an old `Code.gs`
deployed; redeploying is what turns the feature on.

**This cannot be verified from a dev machine** — `google.script.run` only exists inside the Apps
Script sandbox, so a local server or `file://` load can only confirm the localStorage-only
fallback path, never the actual server round trip. See the deployed-URL checklist
at the end of this file for how to check it for real once deployed — in short, a second, independent
browser context (incognito or a different browser) signed into the same account is the only
check that can tell a working round trip apart from `localStorage` simply still being there, and
a second, different account is what confirms preferences aren't leaking between visitors. Nobody
has run that checklist yet as of this writing.

### Where per-user values are stored (2026-10-06)

The three preferences and the saved-filters blob (see "Extended server features" below) are stored in
`PropertiesService.getUserProperties()`, the store of the account the script runs as. This deployment
runs as **User accessing the web app**, so that is each visitor, and each person gets a store of their own
(500 KB per person, which private VVD notes share) that nobody else can read. Keys: `bfrPref:bookingFlashDarkMode`,
`bfrPref:bookingFlashAutoRefresh`, `bfrPref:bookingFlashFreezePanes`, `bfrPref:bookingFlashFilterPrefs`.

**Why it moved.** Until 2026-10-06 these values were in the shared **script** properties, one key per person
(`bfrPref:<email>:<name>`). Script properties have one 500 KB limit for the whole project, admin keys
included, and the filter blob can be up to 8,000 bytes a person: about 60 heavy users would fill it, and
then every preference save and every admin property write would fail.

**Guard.** The server uses a person's own store only when the account the script runs as (the effective
user) is the visitor, the same check private VVD notes use. If the deployment were ever switched to
**Execute as: Me**, every visitor would share the owner's user store; the check sees that and falls back to
the old script-property keys, exactly as before, so one person's settings never show for everyone.

**Old values move over by themselves.** The first time a person's page loads after the new `Code.gs` is
deployed, a value found only under their old script key is returned, copied into their own store, and the
old key is deleted once the copy has been read back. If the copy fails (for example their store is full),
the old key is kept and the next load tries again. Once every old key has moved (or there were none), a marker,
`bfrPref:legacyChecked`, is written to the person's store and their old script keys are not looked up again
(2026-10-07): a page load then reads the person's store with one call and the shared store not at all. Its one
limit: if the deployment were ever switched to **Execute as: Me** and back, values saved in between (which go to
the old script keys, see "Guard") would not move again for people who already have the marker. Saving a value also deletes that person's old key.
Nothing reads or deletes another person's keys, and the client (the app's HTML) is unchanged: the same
functions, arguments, replies and limits. A person who never opens the report again keeps their old script
keys; they are harmless and can be deleted by hand (Project Settings -> Script Properties, names starting
`bfrPref:` followed by an email address).

`tests/check_server_extras_logic.js` covers isolation between two people, the move from the old keys
(including a failed copy), the fallback, and the error replies, against fakes. **UNCONFIRMED in production**
until the deployed-URL checklist below has been run: step 4 (a second account does not see the first
account's setting) and, for the move, one account that had saved settings before the redeploy confirming
they are still there afterwards.

### `?check=identity` was removed (2026-10-06)

`Code.gs` used to serve `?check=identity` (`runIdentityProbe_`), a temporary diagnostic that asked whether
`getUserProperties()` gives each visitor their own store under **Execute as: Me**. No result was ever
recorded. Its question no longer applies: the deployment runs as **User accessing the web app**, so the script runs as
the visitor by construction. The answer is recorded under "`?check=identity`: the answer, recorded
2026-10-06" near the end of this file, and the `doGet` branch and the function were deleted. A request with
`?check=identity` now just loads the report.

**Leftover data.** Anyone who did open `?check=identity` left a user property named
`bookingFlashIdentityProbeStamp` holding their email address and a time: in their own store if the deployment
ran as the visitor then, in the owner's store if it still ran as **Execute as: Me** (before 2026-09-28). It is
harmless and nothing reads it. A user property can only be deleted by code running as that account, so since
2026-10-07 the page load does it: `doGet` deletes `bookingFlashIdentityProbeStamp` from the visitor's own store
whenever it finds it there (it is in the same read as the preferences, so this costs nothing when it is absent).
A stamp in the **owner's** store, from the Execute-as-Me days, goes the next time the owner opens the report. A
person who never opens the report again keeps theirs; only they can remove it.

### Extended server features: filter-prefs sync, Drive export (2026-09-28)

Alongside the three-boolean server-backed prefs above, `Code.gs` now also
persists a per-user copy of `FilterPrefsStore`'s filter blob and backs an
on-demand "Export to Drive" button in Settings. Full design reasoning is in
`docs/SERVER_PREFS_CONTRACT.md`'s "Addendum (2026-09-28)" section and
`Code.gs`'s own comment above `readServerExtras_`; this is just the
deployment-relevant part. (A schedule-change digest email was also built in
this PR and archived before deploying — see that addendum's "Archived"
section.)

**Runs as the visitor, not the deploying account.** This deployment is
"Execute as: User accessing the web app" (changed 2026-09-28). Exports are
created in the visitor's own Drive. To switch an existing deployment:
**Deploy → Manage deployments → pencil → Execute as: User accessing the web
app → New version → Deploy** (same `/exec` URL). Under the old "Execute as:
Me", exports landed in Kevin's Drive behind a link the visitor couldn't open.

**Consent on first open, per user.** After the redeploy, each person sees a
one-time Google consent screen for Drive. There is no Gmail or Calendar
scope — the app has no calendar features (removed 2026-10-01), and the date-cell
link to the OPUS vessel schedule is a plain client-side link.

**Until redeployed**, none of this does anything — `window.__SERVER_EXTRAS__`
is simply never injected, and every gated code path treats that as
unavailable, exactly like the three-boolean prefs feature degrades on an
old `Code.gs`.

**A "Booking Flash Snapshots" folder is created automatically** in the
visitor's own My Drive the first time they export.

**This cannot be meaningfully verified from a dev machine**, for the same
reason the three-boolean prefs can't: `google.script.run` only exists inside
the Apps Script sandbox. A local run can only prove the app degrades
correctly when `window.__SERVER_EXTRAS__` is absent. To verify for real,
after redeploying:

1. Open the `/exec` URL, set a filter (e.g. select a Lane), and confirm it
   is still selected after a reload in an **independent** browser context
   (incognito or a different browser) — the discriminating check, same as
   the three-boolean prefs' own checklist.
2. As a **second, non-deploying account**, click "Export to Drive" and
   confirm the Sheet appears in *that account's* "Booking Flash Snapshots"
   folder and the "View in Drive" link opens it. Nobody has run this
   checklist yet as of this writing.

## Shared view links: `?view=` and `window.__SHARED_VIEW__` (roadmap slice 4.2, 2026-10-05)

`doGet` can now hand the page a **shared view link**: `<exec-url>?view=v1.<payload>.<check>`, the text
`BFShared.encodeView` writes (format and limits: `shared/30_view_codec.js`). The page runs inside Apps
Script's sandbox iframe, whose own address is not the one the visitor typed, so the server passes the link in
the way it passes `__EXEC_URL__` and `__SERVER_PREFS__`: an inline script placed before the app's babel block.
(Google also documents `google.script.url.getLocation()`, which gives a page in that frame the visitor's query
parameters. Slice 4.3 may be able to use it and skip this echo; whether it works for this app is
**UNCONFIRMED** until run on `/exec`. This server half is built first because it is cheap and dormant.)

**This is dormant. The app does not read `__SHARED_VIEW__` yet (slice 4.3, not built).** Deploying the code
changes nothing a visitor can see, and the only way to check it is to read the global in the browser
console. What `Code.gs` does:

- `?view=` holds a string that `BFShared.decodeView` accepts (it reports no `errors`; the codec refuses
  anything over 4,000 characters (`viewCodec_MAX_ENCODED_CHARS`), and `Code.gs` uses the same 4,000 for its cheap
  first gate that keeps a huge value away from the decoder; it was 8,000 once, which only added a dead range): the page gets `window.__SHARED_VIEW__ = "<the original link text>"`, a JSON string. It is the
  link as typed, not the decoded view. The client decodes it again with its own valid sets (stale sale
  weeks and the like are dropped and reported there), and decoded text stays untrusted.
- Anything else (no `view`, a damaged or tampered link, a wrong version, longer than 4,000 characters, a
  repeated `view=`, a page without the babel marker, `Shared.gs` not pasted): the page is returned **byte
  for byte as before** and `__SHARED_VIEW__` is simply absent. The function never throws, so it cannot
  break page load. A link that is refused is refused silently, with no message to the visitor.
- The text is escaped for an inline script (`<`, `>`, `&`, U+2028 and U+2029 as `\u` escapes). A link that
  passes the check holds only letters, digits, `-`, `_` and `.`, so this is a second layer, kept in case the
  link grammar is ever widened. `tests/check_shared_view_injection.js` proves it with a decoder that
  accepts anything.
- `apps-script/basic/Code.gs` is **unchanged**: the basic deployment has no `Shared.gs`, so a shared link
  opened there loads the default view, silently. Supporting it would mean pasting `Shared.gs` (pure logic, no
  Google services) into that project and copying this function, which is a decision for Kevin.

**Needs the new `Code.gs` and `Shared.gs`.** Add a script file named `Shared` (**+** next to *Files* ->
**Script**), paste `apps-script/Shared.gs` into it (it is generated; never edit it), paste the updated
`Code.gs`, then **Deploy -> Manage deployments -> edit (pencil) -> New version -> Deploy** as for any
`Code.gs` change. File order does not matter. With `Shared.gs` missing the page loads exactly as before.

**What a local run proves, and what only `/exec` can.** `tests/check_shared_view_injection.js` (181
assertions) runs the real `Code.gs` and `Shared.gs` against fakes. It proves the injection and that hostile
input leaves the page unchanged. It does **not** prove that Google passes `?view=` to `doGet`, that the
parameter survives sign-in, or that the page receives the global. Every item below is **UNCONFIRMED** until
the person named in decision D8 has run it and written the result in the PR.

## Historical archive: the team's folder of daily Sheets (2026-09-30)

The 🗓️ Historical Data popover reads the team's Drive folder of **one Google Sheet per day** (the
folder id is `ARCHIVE_FOLDER_ID_` near the top of the archive section in `Code.gs`). People keep
adding a Sheet per day by hand, as today. The script **only reads** the folder: it never creates,
edits or deletes anything there, and there is no timer.

- **Dates come from file names.** The folder's own naming, `Booking Flash Report Data-09302026`
  (MMDDYYYY), works, and so does any one date in the name: `2026-09-29`, `20260929`,
  `9-29-2026`, `9.29.26`, `Sep 29 2026`, `September 29, 2026`. Numeric dates are read **month
  first** (US). A name with no date, or with two different dates (a range), is skipped. If two
  Sheets share a date, the one edited most recently is used.
- **Only each Sheet's first tab is read.** Its first row must be the export's header row (it must
  contain `Vessel 1st VVD`). The Sheets hold only the export's columns; the server adds the
  `Record Date` column from the file name, so the app sees exactly the old archive's shape. A Sheet
  that already has `Record Date` as its first column is used as-is.
- **New Sheets show up within 10 minutes.** The date list is cached for
  `ARCHIVE_INDEX_CACHE_SECONDS_` (600 s).
- **Why per-day at all:** the old single archive Sheet caps at 10 million cells (~105 days at ~95,000
  cells a day, so around early December 2026), and loading all of it was 15.9 MB / ~14 s at ~22k
  rows. Now the app downloads the date list and only the day(s) someone opens.

**Nobody needs the folder shared with them (2026-09-30).** The web app runs as the visitor, and
Drive only serves a visitor what is shared with them. So the admin's 30-minute data-feed trigger
(`refreshDataFeeds`, which runs **as the admin**) also copies the **45 most recent days**
(`ARCHIVE_CACHE_DAYS_`) into the script's shared cache, and the popover reads them from there. A
visitor who can open the folder anyway still sees every date; one who can't sees the cached 45.
Why not every day: the cache keeps an entry at most 6 hours and has no published total size, so
the job re-copies each cached day every 4 hours (and at once when its Sheet is edited), and each
day is about 185 KB compressed. Raising `ARCHIVE_CACHE_DAYS_` works, but more days means more
cache and more work per run (each run stops after 90 s and the next one continues). The 90 s includes
listing the folder, but every run copies at least one day, so a folder slow enough to list that the
listing alone takes the 90 s still fills the cache, one day per run; `refreshArchiveCache`'s result
reports the listing time as `scanMs` (2026-10-06).

If nothing can be read (the cache is empty and the visitor can't open the folder,
`ARCHIVE_FOLDER_ID_` set to `''`, or no dated Sheets), the popover falls back to the old published
Sheet exactly as before.

### `getDataFeed` reply stamp: `fetchedDate`, `refreshIntervalMs`, `changedAt`, `changedDate`, `refreshIntervalMsAtFetch` (roadmap slices 1.1 and 2.2, 2026-10-05)

Every ok `getDataFeed` reply (data, `unchanged` and `older` alike, for both feeds) now carries extra
fields next to `fetchedAt` and `ageMs`. **Purely additive**: an older page ignores them, no existing key
changes, and a `{ok:false}` reply is untouched.

| Field | Value |
|---|---|
| `fetchedDate` | `'yyyy-MM-dd'`: the calendar date of `fetchedAt` **in the script's time zone** (Project settings), not UTC. A copy fetched at 23:30 UTC is 2026-09-01 in New York and 2026-09-02 in Tokyo. The browser does not know the script's zone, so the server says it; slice 2.2 needs it to pick "the previous available archive date" |
| `refreshIntervalMs` | The refresh interval in force **when the reply is built**: `1800000` (30 min) from 08:00 to 16:59 script time (`DATA_FEED_BUSY_START_HOUR_` to `DATA_FEED_BUSY_END_HOUR_`), else `3600000` (60 min). Slice 1.1 turns a stamp amber when it is older than twice this; a page that does not get the field assumes 60 min |
| `changedAt` | ISO time the **current content** (this hash) was first seen. `fetchedAt` (and so `fetchedDate`) advances on **every** download, even when the file is byte-identical, so it is the time of the last *download*, not the data's as-of time. `changedAt` carries over from the previously cached copy when the new download has the same hash, and equals `fetchedAt` when the hash differs. A cached meta written before this field existed (`v` stays `1`) has none: a cache hit then replies with `changedAt = fetchedAt`, and a same-hash re-download hands that old meta's `fetchedAt` over. With no previous meta at all (expired after 3 hours, or evicted early) it restarts at `fetchedAt`, so after an eviction it can overstate how recently the data changed, never understate it |
| `changedDate` | `'yyyy-MM-dd'` of `changedAt`, formatted exactly like `fetchedDate` (script time zone). **Slice 2.2 must use `changedDate`, not `fetchedDate`, as the data's as-of date** when it picks "the previous available archive date" |
| `refreshIntervalMsAtFetch` | The refresh interval in force **when the copy was fetched** (worked out from `fetchedAt` and stored in the cache meta), as opposed to `refreshIntervalMs` which is the interval now. Left out for a copy whose meta predates the field or when the interval could not be worked out |

Each field is worked out on its own and **left out** (never null, never an error) when it cannot be: a
time-zone lookup or date format that throws, or a formatted date that is not `dddd-dd-dd` (`changedAt` needs no time zone, so it survives a failing date format and
only `changedDate` goes). Computing the stamp
cannot turn a good reply into a failed one. **Needs `DataFeeds.gs` redeployed** (paste it, then **Deploy ->
Manage deployments -> edit -> New version -> Deploy**); nothing reads the fields yet, so nothing visible changes.

`tests/check_team_features_logic.js` (now 434 assertions) covers every reply shape in New York, Tokyo, Kolkata,
Kiritimati, Los Angeles and UTC, across the 08:00 and 17:00 edges and a New Year. Its `formatDate` fake is the
platform's own `Intl` (not a canned answer) and its clock is frozen, so the expected values are written by hand
and do not come from the code. It cannot prove how Apps Script's own `Utilities.formatDate` behaves for the
project's real zone, or that `google.script.run` delivers the fields.

## Running a testing version alongside the main one

Per Kevin (2026-09-16): **one `Code.gs` per Apps Script project, not two.** An Apps Script
project is a single global JavaScript namespace, so a second copy of this file in the same
project means two `doGet` declarations and the editor rejects it outright
(`Identifier 'doGet' has already been declared`). The same goes for every other function here.

To have the main version (1.66) and a testing version (e.g. 1.67) both reachable, create **two
separate Apps Script projects**, each with its own `Code.gs`, its own `index.html`, and its own
`/exec` URL. The `Code.gs` source is identical in both — it is version-agnostic and simply serves
whatever HTML is sitting in its project's `index.html`. Nothing in this file needs to know which
app version it is hosting.

Two consequences worth knowing before you debug something that is not a bug:

- **Script and user properties are per-project.** Each project has its own stores, so the preferences saved
  by the server-backed prefs feature (in each person's user properties since 2026-10-06) do NOT cross
  between the two deployments. Dark mode set on
  the testing deployment will not appear on the main one. For testing that is the behaviour you
  want — a testing build cannot corrupt real settings — but do not read it as the feature being
  broken.
- **The update-checker compares against its own project's `index.html`.** Each deployment
  independently decides whether it is out of date, which is correct, but it means a version
  banner on one says nothing about the other.

Label the projects clearly in the Apps Script UI (e.g. *Booking Flash Report App* vs *Booking
Flash Report App — TESTING*). The two `/exec` URLs are opaque and indistinguishable by eye, and
pasting a testing build over the live project is a quiet, expensive mistake to make.

## Server-backed preferences: design notes and the production checklist (moved from AGENTS.md, 2026-09-29)

### Open question for production: do saved settings actually persist?

The app persists three preferences in `localStorage` (`bookingFlashDarkMode`,
`bookingFlashAutoRefresh`, `bookingFlashFreezePanes`). In production it runs inside an Apps
Script HtmlService sandbox iframe whose own `window.location` is a **transient**
`*.googleusercontent.com` URL — the code already works around that for navigation and
update-detection. `localStorage` is keyed by origin, so **if that origin is not stable between
loads, all three preferences silently reset every visit** and no one would file a bug; they'd
just re-toggle dark mode.

This was never tested, and it cannot be tested from a dev machine — it only reproduces on the
deployed `/exec` URL behind the org's Google sign-in. So as of 2026-09-15 the app measures it on
itself: `readStorageProbe()` writes a marker containing the origin that wrote it and compares on
the next load, and Settings shows one line reporting the result (`persisting` / `first-run` /
`origin-rotated` / `unwritable` / `unavailable`).

**Someone needs to open the deployed `/exec` URL twice and read that line.** The answer matters
beyond the three preferences: any future client-side cache keyed to this origin — an IndexedDB
cache of the Babel transform output was the specific idea on the table — would never hit in
production if the origin rotates, so the probe result gates that work. Note the `/exec` URL has
never been recorded anywhere in this repo; `apps-script/README.md` asks for it to be saved and it
wasn't.

**Reading it properly (revised 2026-09-16):** a second load in the *same* browser is a weak
signal — it cannot distinguish "the origin was stable" from "localStorage happened to still be
there." Do the second load in an independent context (an incognito window, or a different
browser) signed into the same account, where `localStorage` starts empty. That is the only
version of the check whose result means what it appears to mean.

**Result recorded 2026-09-26 (Kevin, deployed `/exec` URL, his normal browser):** Settings read
"Saved settings are persisting normally (56 loads on this browser)" and "Cloud sync: active."
`persisting` means the probe found its marker AND the origin that wrote it matched the current
one, so across 56 real production loads the storage origin did not rotate and `localStorage`
persists. That unblocks origin-keyed client caches. "Cloud sync: active" means `doGet` injected
`window.__SERVER_PREFS__` and the server-backed preferences path is live. Still NOT done: the
independent-context (incognito) and cross-account steps of the checklist below, which are what
prove the server round trip and per-user isolation.

### Server-backed preferences (2026-09-16): what was built, and why it took this shape

A four-agent design pass first looked at moving the three preferences (`bookingFlashDarkMode`,
`bookingFlashAutoRefresh`, `bookingFlashFreezePanes`) server-side so they survive an origin
rotation, without writing any client code. That pass is now superseded — a follow-up
implementation actually built it, against a frozen interface contract
(`docs/SERVER_PREFS_CONTRACT.md`) that four agents worked from in parallel: one on `Code.gs`, one
on the app file, one on the regression tests, and this doc. The reasoning below is what still
holds and why the implementation looks the way it does; read the contract itself for the exact
shapes and rules.

- **Superseded 2026-10-06: the values now live in each visitor's `getUserProperties()` store**, guarded and
  migrated as described in "Where per-user values are stored (2026-10-06)" above; the reasoning below is why
  the first version did not, and the email-namespaced script keys remain the fallback when the script does not
  run as the visitor. As written in 2026-09:
  **`getScriptProperties()`, not `getUserProperties()`, namespaced by the visitor's email.**
  Google documents `getUserProperties()` as readable by "the current or effective user" —
  precisely ambiguous under "Execute as: Me", where those differ, and secondary sources
  contradict each other. If it turned out to be owner-keyed, every visitor would share one set
  of booleans, so one person's dark-mode toggle would flip it for the whole org — worse than the
  bug being fixed, and **invisible to every client-side test**, because from the browser's point
  of view the server stored a value and gave it back correctly. `getScriptProperties()` is
  documented unambiguously as script-global, so per-user isolation instead comes from the key
  (`<pref-name>:<email>`), not from an ambiguous API. `Session.getActiveUser().getEmail()` is
  documented to be blank for execute-as-me web apps *but exempted* when the visitor shares a
  Workspace domain with the developer — which is this deployment. If the email doesn't resolve,
  there is no per-user key available, and the feature fails closed to exactly today's
  localStorage-only behaviour rather than falling back to any shared/global key.
- **No async read path, because there is currently no first-paint flash and that is
  load-bearing.** All three prefs use lazy `useState` initializers that read `localStorage`
  *synchronously* during the mounting render; there is no "unknown" state anywhere in the file,
  and every render site assumes there never will be. So reads don't go through
  `google.script.run` at all — `doGet` reads the prefs and injects `window.__SERVER_PREFS__`
  inline *before* the app's own script runs, exactly as `injectExecUrl_` already does for
  `__EXEC_URL__`. The lazy initializers just prefer the injected global over `localStorage` when
  it's available. Writes are the only thing that go over `google.script.run`
  (`saveUserPref`), fire-and-forget; a failed write is never surfaced to the user beyond the
  existing Settings diagnostic line, and is simply overwritten by the next good one.
- **`bookingFlashAutoRefresh` is not normalized with the other two.** It is
  `stored === null ? true : stored === '1'` — it distinguishes "never set" (on) from
  "explicitly off". Dark mode and freeze panes both collapse null/`'0'`/garbage to `false`. The
  contract calls this out explicitly so a backend that treated all three uniformly wouldn't
  silently flip auto-refresh for anyone who had turned it off.
- **The storage probe stays.** It is the only instrument that can show whether either fix —
  this one or a plain client-side one — actually worked in production, and it predates and is
  independent of this feature. Do not remove it as part of this change.

**`?check=identity`: the answer, recorded 2026-10-06.** The probe measured the `getUserProperties()`
ambiguity above, which exists only under **Execute as: Me**, where the account the script runs as (the
owner) differs from the visitor. Since 2026-09-28 the deployment runs as **User accessing the web app**: the
script runs as the visitor, so `getUserProperties()` is the visitor's own store and
`Session.getActiveUser()` is the visitor. That settles the question for this deployment **by its deployment
mode, not by a measurement**: the probe was never run (no result was ever recorded here), and it was deleted
on 2026-10-06 together with its `doGet` branch.

- `activeUserEmail` behaviour: resolves to the visitor, because the visitor is the account the script runs as.
  The server still fails closed when it is blank.
- `getUserProperties()` shared-vs-per-user: per visitor, because the effective user is the visitor. The server
  does not take this on trust: it uses the store only when the effective user equals the visitor (the private
  VVD notes check), and falls back to the email-namespaced script keys otherwise.
- Under **Execute as: Me** the question would still be open; the guard makes the answer not matter.

Its answer is what made the 2026-10-06 move possible: the script-property store turned out to have exactly the
problem this paragraph used to warn about (one 500 KB quota for everyone), and the user store, per visitor under
this deployment mode, avoids it. Still **UNCONFIRMED** on the real deployment until the deployed-URL checklist
below (step 4, a second account) has been run.

#### This cannot be verified on a dev machine

`google.script.run` exists only inside the Apps Script `HtmlService` sandbox. Nothing that runs
on a laptop — `python3 -m http.server`, `file://`, any local harness — has it, so any local test
run of this feature is testing a strict subset of the real path.

**What a local run DOES prove:** the app still works when `window.__SERVER_PREFS__` is absent
(the `undefined` case, which is every local environment) — i.e. that the degrade-to-localStorage
path is intact and first paint is still synchronous with no new "unknown" render state. It also
proves the JS is syntactically valid and that the write path doesn't throw when `google.script`
is undefined.

**What a local run CANNOT prove:** that `doGet` actually injects `window.__SERVER_PREFS__`
correctly, that `saveUserPref` actually persists anything via `PropertiesService`, that the
visitor's email actually resolves the way the contract assumes, that the resolution rule (server
value when available and non-null, else localStorage, else null) picks the right value against
real server data, or — the whole point of the feature — that a preference set in one browser
context actually reappears in a different one. None of that has been exercised yet; nothing has
been deployed.

#### Deployed-URL checklist (do this after redeploying, not before)

Both `index.html` and `Code.gs` need redeploying for any of this to take effect (see
`apps-script/README.md`'s "Redeploying `Code.gs` itself" section — same posture applies here:
until redeployed, the app just keeps doing exactly what it does today, degrading safely to
localStorage-only rather than breaking). Once redeployed:

1. Open the `/exec` URL signed into your own account and change one of the three preferences
   (e.g. toggle dark mode).
2. Reload in the **same** browser. This is a weak signal — it cannot distinguish a working
   server round trip from `localStorage` simply still being there — but it's a cheap first
   check that nothing broke outright.
3. **The discriminating step:** open the same `/exec` URL in an **independent** browser context
   — an incognito/private window, or a different browser entirely — signed into the **same**
   account, where `localStorage` starts empty. If the preference you set in step 1 is already
   correct on first paint (no flash, no flip after load), the server round trip is real. If it
   comes back at the default instead, the write, the read injection, or the identity resolution
   is broken somewhere — the same-browser reload in step 2 would not have caught this.
4. **Cross-account check:** open the `/exec` URL signed into a **different** account (one that
   hasn't touched this preference) and confirm the preference set in step 1 does **not** appear
   there — it should show that account's own default/unset state. This is the check that would
   catch a namespacing bug (e.g. the email not actually making it into the property key), which
   would silently leak one person's settings to everyone. Since 2026-10-06 it is also the check that
   the user-properties store really is per person on this deployment.
   **Migration (2026-10-06):** with an account that saved a preference or a filter **before** the new
   `Code.gs` was deployed, open the report after the redeploy and confirm the setting is still there; then,
   in Project Settings -> Script Properties, its `bfrPref:<that email>:...` keys should be gone (moved into the
   account's own user properties, which the editor does not show).
5. Check the existing storage-probe line in Settings still reports sensibly on both the
   same-browser and independent-context loads — this feature and the probe are answering related
   but different questions (probe: is the origin stable at all; this feature: does the
   server-backed value round-trip correctly), and a regression in one is easy to misread as the
   other.

No one has run this checklist yet. Do not describe this feature as working in production until
someone has.

### What is known about IndexedDB in this embedding (research on 2026-10-05; every row is UNCONFIRMED for this deployment)

The app runs inside the iframe Apps Script wraps around a web app. Google documents that iframe's sandbox
keywords: `allow-same-origin`, `allow-forms`, `allow-scripts`, `allow-popups`, `allow-downloads`, `allow-modals`,
`allow-popups-to-escape-sandbox` (and top navigation only on user activation, standalone projects only), so the
frame keeps its own origin and the sandbox itself does not block storage
([HTML Service: Restrictions](https://developers.google.com/apps-script/guides/html/restrictions)). That page says
nothing about cookies, localStorage or IndexedDB. The frame's address is a `googleusercontent.com` host (this README, above)
while the page around it is on `script.google.com`, so for a browser's storage rules the app is a **cross-site, third-party
iframe**. That is inferred here; step 1 below reads `location.ancestorOrigins` to confirm it.

**No source found says whether IndexedDB works, or fails, in an Apps Script web app.** The only Apps Script storage
reports found concern localStorage: a 2022 community post that says localStorage entries are per web app and visible
in DevTools ([google-apps-script-community](https://groups.google.com/g/google-apps-script-community/c/2wDmEQr3_CI)), and a
2021 post where `ui.showModalDialog` fails with "Failed to read the 'localStorage' property from 'Window': Access is denied
for this document" while Chrome's "Block third-party cookies" is on
([google-apps-script-community](https://groups.google.com/g/google-apps-script-community/c/Yaeavk6PuXk)).

| Browser / window | What the sources say | What it would mean for the cache |
|---|---|---|
| Chrome, normal window (Edge is Chromium too, but its own tracking-prevention levels are not covered by these sources) | Since Chrome 115 storage in a cross-site iframe is **partitioned**: keyed by the top-level site and the frame's origin, IndexedDB and localStorage included ([Chrome: storage partitioning](https://privacysandbox.google.com/3pcd/storage-partitioning)) | Should work: one copy for (`script.google.com`, this frame's origin). It is not shared with any other site, and is lost if the frame's origin rotates (the localStorage probe below says it did not, in one browser) |
| Chrome, Incognito, or "Block third-party cookies" on | Incognito blocks third-party cookies by default and keeps no site data after the last Incognito window closes ([Chrome Help](https://support.google.com/chrome/answer/95464)). With all cookies blocked Chrome refuses localStorage ("Access is denied for this document") and IndexedDB ("The user denied permission to access the database") ([tomayac, 2022](https://blog.tomayac.com/2022/08/30/things-not-available-when-someone-blocks-all-cookies/)) | **Probably no cache.** Local experiment (Chromium 141, local test pages, third-party cookies blocked with a Chromium test flag, a cross-site iframe carrying Apps Script's sandbox keywords): localStorage threw `SecurityError` and `indexedDB.open` failed with `UnknownError: The user denied permission to access the database`; with third-party cookies allowed both worked. That is not a real Incognito window and not Apps Script, so it predicts, it does not prove |
| Safari (macOS, iOS) | Third-party LocalStorage and IndexedDB are "partitioned per first-party website and also made ephemeral" ([WebKit: Tracking Prevention](https://webkit.org/tracking-prevention/)); a summary says the partitioned store "is also cleared between application launches" ([cookiestatus.com](https://www.cookiestatus.com/safari/)). Separately, ITP deletes a site's script-writable storage, IndexedDB included, after seven days of Safari use without the user interacting with that site ([WebKit: Full Third-Party Cookie Blocking](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/)) | Expect a copy that lasts **at most until Safari is quit**, so it can bridge a flaky network inside one session but not a night. The seven-day cap is then not the limit, the ephemeral store is. Safari 14.x also had a bug where the first `indexedDB.open` of a page never answered ([WebKit bug 226547](https://bugs.webkit.org/show_bug.cgi?id=226547), fixed in 14.7), so reading the cache needs a timeout |
| Firefox | Total Cookie Protection is the default for all users since 14 June 2022 and partitions all storage in third-party contexts ([cookiestatus.com](https://www.cookiestatus.com/firefox/), [Mozilla](https://blog.mozilla.org/en/mozilla/firefox-rolls-out-total-cookie-protection-by-default-to-all-users-worldwide/)) | Should work, partitioned, like Chrome |
| Firefox, private window | IndexedDB did not work in private windows ([Bug 781982](https://bugzilla.mozilla.org/show_bug.cgi?id=781982)); Firefox 115 was to enable it ([Intent to ship, 16 May 2023](https://groups.google.com/a/mozilla.org/g/dev-platform/c/yy7uUP47KGQ)) | Works only from 115, and only for that private session |
| Any private window | Site data is discarded when the private session ends | A cache written in a private window cannot help the next visit |

The summaries above came from fetched pages summarised by a tool on 2026-10-05, not read verbatim: reread the source
before relying on a sentence.

**The cache is best effort, and that is the design, not a defect.** Any of these browsers can refuse the store,
partition it so that it is empty on the next visit, delete it (Safari quitting, a private window closing, a user clearing
site data, storage pressure) or hang the open call, and the page often cannot tell which. So the page must treat every
IndexedDB call as optional (`try/catch` around each, a timeout on the open, and never anything that waits on it
before the first load), show **no** cache banner when there is nothing cached, and behave exactly as it does today when the cache is
unavailable. The cache turns "first load failed" into "shows older data, with a banner" **when it happens to be there**; it
does not turn the report into an offline app.

**What the app already knows about storage in this frame.** `readStorageProbe()` writes a localStorage marker holding the
origin and a load count, and the next load compares them; Settings shows the verdict (`persisting`, `first-run`,
`origin-rotated`, `unwritable`, `unavailable`). The recorded result (2026-09-26, Kevin, deployed `/exec`, "his normal browser",
the browser is not named): "Saved settings are persisting normally (56 loads on this browser)". That is the best evidence
that a browser keeps this frame's storage, and its limits are plain: it is **localStorage, not IndexedDB**, one browser,
no private window, no Safari or Firefox, and the independent-context step of that checklist was never run. The probe's
`unwritable` / `unavailable` lines are free indicators here: read them (step 2) in every browser and window you test.

Expectations this checklist assumes where the contract above is silent (a build that chooses otherwise should change the
expectation, in the same PR): (a) when cached data is on screen, the stamp shows the **cached copy's own saved time**, never
the current time, and is amber when that is older than 2 x `refreshIntervalMs`; (b) the live cache is written only by a
successful live load, never by a manual upload, a historical day, or a feed that failed the data check; (c) a stamp that has
no time to show says so instead of showing nothing.

Probe for step 1 (paste it into the console of the inner frame; it touches only a database named `bfProbe` and a key named `bfProbe`, and removes both):

```js
(async () => {
  const out = { origin: location.origin, top: (location.ancestorOrigins && location.ancestorOrigins[0]) || '(not exposed)', localStorage: null, indexedDB: null };
  try { localStorage.setItem('bfProbe', '1'); localStorage.removeItem('bfProbe'); out.localStorage = 'ok'; } catch (e) { out.localStorage = 'FAILED ' + e.name; }
  try {
    const db = await new Promise((res, rej) => {
      const timer = setTimeout(() => rej(new Error('no answer in 3 s')), 3000);
      const q = indexedDB.open('bfProbe', 1);
      q.onupgradeneeded = () => q.result.createObjectStore('s');
      q.onsuccess = () => { clearTimeout(timer); res(q.result); };
      q.onerror = () => { clearTimeout(timer); rej(q.error); };
      q.onblocked = () => { clearTimeout(timer); rej(new Error('blocked')); };
    });
    await new Promise((res, rej) => { const tx = db.transaction('s', 'readwrite'); tx.objectStore('s').put('x', 'k'); tx.oncomplete = res; tx.onerror = tx.onabort = () => rej(tx.error); });
    const got = await new Promise((res, rej) => { const g = db.transaction('s').objectStore('s').get('k'); g.onsuccess = () => res(g.result); g.onerror = () => rej(g.error); });
    db.close(); indexedDB.deleteDatabase('bfProbe'); out.indexedDB = 'ok (read back ' + got + ')';
  } catch (e) { out.indexedDB = 'FAILED ' + (e && e.name) + ': ' + (e && e.message); }
  console.log(JSON.stringify(out));
})();
```
